# 科研失败诊断

目标：把“效果不好”转成有证据的原因判断和能够推进的下一步，避免在同一路线上反复修补。

## 1. 还原失败现场

先读取项目现有 Spec、原假设、验收条件，以及本次实际使用的代码、配置、数据划分、日志和结果。只读取与问题有关的历史与材料，复用现有记录。

明确：预期是什么、观察到了什么、与哪个基线比较、差距是否稳定、本次运行能否定位。缺失证据标为未知，不补造运行事实。

先区分接口超时、工具失败、任务未执行与研究结果失败；派单成功、进程退出、文件存在都不能单独证明实验有效。

## 2. 按证据检查原因

依据症状选择顺序，不要求每次机械检查全部项目：

| 层面 | 关键问题 | 可用检查示例 |
| --- | --- | --- |
| 评价 | 指标和比较对象是否正确？ | 已知答案样例、指标重算、样本与标签对应 |
| 实现 | 是否忠实实现已讨论的方法？ | 追踪公式到代码、梯度和张量路径、与参考实现对照 |
| 数据 | 数据是否真的支持目标？ | 原始样例可视化、标签质量、预处理、划分与泄漏检查 |
| 训练 | 是否学到了东西，训练是否充分？ | 损失曲线、小批量过拟合、优化器与检查点核验 |
| 实验设计 | 结果是否排除了替代解释？ | 合适的基线、消融、负对照、重复性和不确定性 |
| 假设 | 方法前提是否成立？ | 最小机制验证、适用边界、相关文献与失败案例 |

不能只因跑了很多轮就称训练充分；不能只因程序能跑就认定实现和数据正确；负结果只支持实际测试过的条件。

## 3. 设计最小区分检查

为主要候选原因提出最便宜且能区分解释的检查，写明：输入和操作、不同结果各支持什么、下一步分支、停止条件。优先使用现有证据和小样例，避免直接扩大模型、数据或参数搜索。

当涉及陌生现象、方法实现细节或现有检查无法区分原因时，检索并阅读真实论文、官方文档、开源实现或相关问题记录；记录来源及其与当前问题的关系，区分来源结论与自己的推断。

只在已有授权、资源和数据条件内实施修复与检查。用户仅要求分析时交付诊断；已授权执行时推进普通技术处理，不把它们一律交回用户。改变核心研究问题或需要新增权限时再澄清。

## 4. 给出可接续的结论

简要输出：

- 失败现象与关键证据位置。
- 已确认原因、候选原因和仍未知的内容。
- 最值得先做的检查及结果分支。
- 建议继续、修复、补证或转向的理由。
- 下一步负责人、具体交付物和验收条件。

写入项目已有失败记录或实验记录；没有需要持久化的结论时无需新建账本。不重复没有新信息的检查，不重放副作用未知的操作，不降低原验收标准来宣称成功。

本技能提供诊断流程；等待、重试、任务交接和重启恢复由现有 Harness 负责。
