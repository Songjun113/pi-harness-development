# Pi 内持续接续

## 已核实的能力与限制

本工作流使用 npm:pi-goal。它在活动 Goal 的 agent_end 后接续同一 Pi 会话，不需要也不启动旧 Codex 后台。Goal 状态跟随当前会话分支；重新加载会暂停活动 Goal，需要用户恢复。Pi 进程不运行时没有持久后台保证。

使用前读取当前安装版本的 pi-goal 文档，核实实际工具。已知版本提供 create_goal，活动时提供 get_goal/update_goal；模型的 update_goal 仅支持 complete。暂停/恢复/清除由用户 `/goal pause`、`/goal resume`、`/goal clear` 控制。不要编造 pause 工具或声称已经自动暂停。

## 明确授权

用户仅说“公司，启动！”时，核实项目、工具和下一步，准备协作；不据此调用 create_goal。若用户已在本次项目明确要求启动/设置/恢复 Goal，按该授权执行，无需重复询问。

完整启动表达示例：

> 公司，启动！并启动 Goal：按当前项目 Spec 的已确认目标持续推进，由当前 GPT 主模型主管、Gemini 3.8 Flash High（flash-high）监督，完成后停止；遇到真实权限、人审或监督阻塞时报告并等待我处理。

这是未来项目启动示例，不是安装本技能时对任意科研项目的授权。创建前应把“当前项目”展开为实际根目录、Spec、具体目标、验收证据与资源边界；不能拿泛化示例直接建立空目标。

## Goal 合同

读取 pi-goal-writer。形成自包含合同，至少覆盖：

1. 具体项目与当前授权的总目标/阶段目标。
2. 完成时可检查的产物和现有 Spec 验收条件。
3. 数据、目录、外部作业、资源和权限边界。
4. GPT 主管、flash-high 监督与子 Agent 职责。
5. 每轮选择下一缺口、执行、独立复核、回写 Spec 和接续策略。
6. 完成停止与真实阻塞处理；禁止将阻塞标为成功。

仅在用户明确要求 Goal 且工具实际可用时创建；已有 Goal 先核实内容，不能覆盖不同目标，也不擅自设 tokenBudget。若没有 get_goal 可用，不能从工具缺失推断一定没有旧 Goal，应让用户查看 `/goal status`。

创建后保留真实工具回执，区分“合同已草拟”“Goal 已激活”“科研任务已执行”。活动 Goal 每轮只读必要的当前状态，不重读整个项目历史。

## 阻塞、暂停与恢复

现有 pi-goal 没有供模型调用的 pause，因此不能承诺技能能自动暂停 Goal。

- 关键监督不可用或真实权限/人工依赖阻塞时，记录受影响要求、已尝试路径和解除条件；有不依赖该阻塞的已授权任务可先完成。
- 无合理可推进任务时明确请求用户执行 `/goal pause`，不要把 update_goal(complete) 用作暂停，不制造假进展或重复审核请求。
- 在用户暂停前，Goal 可能继续触发后续轮次。这是当前接续机制的已知限制；不得宣称“已自动停止”。若继续触发，只复核新反馈/解除证据，不重复失败调用、实验或写相同日志，提醒用户暂停。
- 用户输入“暂停”但工具不能执行时，明确给出 `/goal pause`；不声称已经完成命令。
- 用户解除阻塞后，先核实原作业、已交付内容及 Spec，再由用户 `/goal resume`；不要重复未知副作用任务。
- 仅在真实达成 Goal 合同并核验必需证据后调用 update_goal(status="complete")。阶段回复结束不等于整个 Goal 完成。

## 推荐运行方式

单个项目、一个主管主会话、一份 Spec、一个活动 Goal。监督只在关键节点调用，正常运行等待工具结果。先用隔离小项目验证一轮交接与收尾，再应用到真实训练项目。

本技能文档及加载检查不能证明真实科研已持续运行。发布时分别报告文档/加载验证、独立监督实际调用和真实项目循环的验证范围。
