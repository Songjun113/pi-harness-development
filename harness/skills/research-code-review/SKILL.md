# 科研代码复核

目标：判断代码是否完成预期研究方法，以及已有证据能支持哪些结论。

## 1. 固定审核对象

读取当前 Spec、约定的方法、相关论文原文或参考实现，以及实际代码、配置、数据入口和已有测试。明确审核版本、范围和已知差异，避免审核错版本或把旧结论套到新实现。

对仅请求审核的任务默认只读；获得修复授权后再改代码。保持现有技术栈、测试方式和记录格式，不为审核另建框架。

## 2. 从研究方法追踪到实现

追踪关键假设或公式对应的模块、函数和数据流，重点检查会改变结论的环节。按实际风险选择：

- 数据单位、坐标、时间对齐、索引、张量维度和标签生成。
- 参与者或来源划分、训练与测试隔离、预处理拟合范围及泄漏。
- 方法结构、损失、约束、梯度路径、冻结参数和优化器行为。
- 训练与推理模式、检查点选择、训练充分性的实际证据。
- 指标实现、基线公平性、统计单位、对照及结果汇总。
- 已知答案、边界情况、数值稳定性和异常数据处理。

需要查证方法时读取真实原文、官方文档或原始代码；不凭摘要或模型自信推定实现正确。对有意简化的实现说明其影响，而不是自动认定错误。

## 3. 以最小检查验证疑点

优先复用已有测试；针对具体风险补充小样例、已知答案、数据流断言或必要的对照。检查应能发现实际行为错误，不只复述实现。

只执行授权范围内的检查，不擅自开始大规模训练。分别报告代码阅读、静态检查、实际运行与结果核验；未运行就写未运行，不把建议的测试写成已通过。

## 4. 交付审核结论

先列具体问题，按影响排序；每条包括代码文件与行号、触发条件、对结果的影响、证据或复现方式、最小修复建议。没有可定位问题时，说明实际检查范围和剩余不确定性。

结论可为通过、需修改或证据不足，但仅适用于本次范围：

- 工程能运行，不代表方法实现正确。
- 实现符合方法，不代表数据可信或研究假设成立。
- 局部测试通过，不代表全部实验或科学结论通过验收。

不增加 Spec 未要求且无具体风险依据的验收门槛，不把独立模型审核冒充必要的真人、设备或科学验证。写入现有审核记录，向主管交付明确的修复项及复查条件；无关内容无需重复汇报。
